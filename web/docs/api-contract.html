lovdex-cli 前后端接口契约

为前后端拆仓定义的全量接口契约：WebSocket 入站/出站帧 + 全部 HTTP REST 路由 + shared 共用类型/工具 + 鉴权 + 构建边界。配套 系统架构图。

1. 概述

通信以 WebSocket /ws 为主（流式 chat），辅以 HTTP REST /api/*（CRUD、列表、搜索、上传）。所有 WS 帧为 JSON，通过 type（入站）或 kind（出站）字段路由。

WS 路径 固定 /ws，与 HTTP server 同一进程升级（ws.WebSocketServer({server})）。生产同源；开发经 Vite proxy /ws → ws://host:SERVER_PORT。

REST 信封 成功：{ success: true, data: T }；错误：{ success: false, error: { code, message, details? } }。前端读取 body?.data ?? body。

sessionId 语义 全程使用 app 侧 sessionId；provider 原生 sessionId（claude 的 uuid / codex 的 thread-id）不外泄，仅后端 DB 内映射。

3. WebSocket 入站帧

客户端 → 服务端，JSON，按 type 路由（chat-websocket.service.ts）。

type字段触发动作
chat.sendsessionId* · content(string) · options?{model, effort, permissionMode, toolsSettings, skipPermissions, sessionSummary, images}解析 session → startRun → 过滤 images（仅允许 ~/.cloudcli/assets 下）→ 调 provider spawn → 完成后 completeRunIfCurrent 兜底
chat.abortsessionId*取 run → provider abort → completeRun 发 complete{aborted:true}
chat.subscribesessions:[{sessionId, lastSeq?}]对每个：若 processing 则 attachConnection；查 pending permission；回 chat_subscribed；重放 seq > lastSeq 的缓冲事件
chat.permission-responserequestId · allow(bool) · updatedInput? · message? · rememberEntry?调 resolveToolApproval(requestId, ...)（仅 Claude 有交互式审批）

非法入站 → protocol_error 帧，code 取 UNKNOWN_MESSAGE_TYPE / SESSION_ID_REQUIRED / SESSION_NOT_FOUND / UNSUPPORTED_PROVIDER / RUN_IN_PROGRESS / NO_ACTIVE_RUN / INTERNAL_ERROR。

4. WebSocket 出站帧

服务端 → 客户端，JSON，按 kind 区分。每条 live 帧由 decorateAndRecordEvent 分配单调递增 seq 并把 sessionId 重映射为 app 侧 ID。

10. 拆仓清单

当前单仓已具备拆仓条件：构建独立、产物独立、runtime 依赖零重叠。拆仓需处理：

  1. 提取 shared 包：把 NormalizedMessage / MessageKind / GatewayEventKind / ServerEventKind / ApiSuccessShape / McpScope / McpTransport 等协议类型 + networkHosts.js 提为一个独立 npm 包（如 @lovdex/protocol），前后端各自依赖。消除前端镜像定义。
  2. 对齐 LLMProvider：统一为 'claude'|'codex' 或显式区分"前端可选 provider"与"后端支持 provider"。前端的 cursor/opencode 走外部服务，需明确边界。
  3. REST 信封统一：前后端共用 ApiSuccessShape 类型，前端 authenticatedFetch 的 body?.data ?? body 容错保留。
  4. WS 协议固化：入站 4 种 type + 出站 kind 集合写入 shared 包，作为不可破坏契约。
  5. 静态托管解耦：拆仓后生产部署有两种选择 — (a) 后端继续 express.static 托管前端 dist/（同源，最简单）；(b) 前端独立部署到 CDN/Nginx，后端只提供 /api + /ws（跨域，需 CORS + WS 跨域）。当前 server/index.js:145 的静态托管 + SPA fallback 可作为 (a) 的参考。
  6. vite proxy 仅 dev：vite.config.js 的 /api、/ws proxy 是开发期转发，拆仓后保留；生产用 (a) 或 (b)。
  7. 环境变量切分：VITE_IS_PLATFORM 共用，SERVER_PORT/HOST 后端，VITE_PORT 前端 dev。拆仓后各自 .env。
  8. 前端独立镜像的 NormalizedMessage 字段差异（parentToolUseId/isFinal）需并入 shared 类型或确认前端专用。
