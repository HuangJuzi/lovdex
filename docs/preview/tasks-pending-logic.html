待办处理逻辑 · 定稿方案

一个任务 = 一个会话 = 一个面板。既然一次只展开一个面板，就不需要「多面板并发」那套复杂设计 —— 每个面板内部是一个串行队列，一次答一个。

我替你定的六件事 附理由

问题决定理由
同时有多个待办 串行队列，一次只显示一个 一个 panel 一个会话；后端 canUseTool 本来就是 await 完这个才执行下一个工具，实际极少并发。前端再堆成一列反而占地方。 但数据层仍按数组存（后端 Map 无锁），所以真出现并发也不会丢——只是排成队一个个答。
先答哪个 会超时的排前面 普通工具 60 秒后自动拒绝，AskUserQuestion / ExitPlanMode 是 timeoutMs: 0 永远等。会自己死掉的先处理，不会死的可以等着。 排序键：超时时刻 升序，无超时的排最后。
倒计时显示 只在会超时的上面显示 倒计时是真信息、能防你被静默自动拒；「永远等」是假紧迫感，显示它只会让你白紧张。 剩余 <15 秒变红加粗，并提示「超时会自动拒绝，可去会话里继续」。
其他模式下没有待办 面板正常显示，只是没有待办区 auto / bypassPermissions 下 SDK 直接跳过 canUseTool，无人值守任务按策略直接拒交互工具。 所以待办区是条件渲染，不是面板的固定区块 —— 没待办时面板回到纯粹的「看任务 + 快速回复」。
兜底入口 保留，但降为次要链接 面板没渲染出待办（时序、断线重连、客户端版本不一致）时，你仍要有路可走。 从现在的唯一按钮「去处理」降级为底部小链接「在会话里处理 →」，不占主视觉。
答完的反馈 就地淡出 + 自动切下一个 答复帧发出后前端乐观移除（现有实现已经这么干），队列自动前进到下一个。不需要你手动关。 若后端回 permission_cancelled 或答失败，把该项标灰并说明原因，不静默消失。

✓ 为什么这样最省事

  • 不新增数据模型：待办还是后端那套 requestId + input，前端只是换个挂载点渲染同一批组件
  • 不新增接口：答复沿用 chat.permission-response，发送沿用 chat.send
  • 只改一处作用域：把 pending 请求的接收从「当前打开的会话」放开到「当前展开的任务」
  • 队列逻辑极薄：排序键一个字段，显示取队首，答完出队 —— 不需要状态机

⚠ 三个必须写进实现的约束

  • 超时是自动拒绝，不是自动通过 —— 所以倒计时必须显眼，且只在会超时的条目上
  • 执行中不能发消息：后端 RUN_IN_PROGRESS 无队列，回复要走前端待发队列等这轮结束（④ 的输入框提示）
  • 会话被清理（无 session_id）时待办区与回复区都不渲染，只留「重新执行」

一个我没替你定的

  • 「总是允许」的 allowedTools 是写进会话级 sdkOptions 的（claude-sdk.js:955），只对这个会话后续有效，不是全局。
  • 在面板里点它，和会话页点它是同一个效果。要不要在面板里额外提示「仅本次会话有效」？我倾向要 —— 否则容易被误解成全局设置。
