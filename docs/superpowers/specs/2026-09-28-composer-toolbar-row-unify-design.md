# 手机端输入栏按钮排布统一 设计

日期：2026-09-28
状态：已确认，待写实现计划
上游：`2026-09-18-mobile-permission-mode-label-design.md`（手机端模式标签可见性 —— 本设计修的是它带出来的副作用）

## 0. 问题

手机端会话页，只有 **Approve（自动审批）** 模式下底部输入栏的工具按钮会折成 3 行，其它五个模式都是 2 行。

用户原话是「输入的工具显示成 3 行」；澄清后确认指的是**底部输入栏那一排按钮**（附件、权限模式、模型、effort、token、发送…），**不是**对话里的工具调用行。

### 根因

底部工具栏是 `PromptInputTools` 的 `flex flex-wrap items-center gap-1`（`web/src/shared/view/ui/PromptInput.tsx:129`），首行依次放：附件按钮、文件按钮、模式按钮、模型按钮（`Cpu` 图标 + `max-w-24`=96px 的名字上限）。

模式按钮是**内容自适应**宽度，于是六个模式的占位各不相同。375px 实测（`toolsW` = 293px）：

可用宽度 `toolsW = 视口 − 82`。这 82px 的构成：composer 外壳 `px-2`（8×2）+ `PromptInput` 左右边框（1×2）+ footer `px-3`（12×2）= 82（实测 344–600px 恒定，见 §5）。

| 模式 | 短标签 | 模式按钮宽 |
|---|---|---|
| plan | `Plan` | 58px |
| auto | `Auto` | 61px |
| acceptEdits | `Accept` | 71px |
| bypassPermissions | `Bypass` | 73px |
| default | `Default` | 74px |
| **autoApprove** | `Approve` | **80px** |

`Approve` 是六个短标签里唯一 7 个字符的，比 `Default` 宽 6px。**这 6px 就是全部原因**：折行只由首行放不放得下决定，所以 Approve 在「刚好差几 px」的那些宽度上会先折，其它模式不会。

逐像素扫描（步进 1px）复现了这个次序：

| 视口 | 行数（Default / Auto / Approve / Accept / Bypass / Plan） |
|---|---|
| 353px | 3 / **2** / **3** / 3 / 3 / **2** |
| 361px | 3 / 2 / **3** / 3 / 3 / 2 |
| 367px | **2** / 2 / **3** / 2 / 2 / 2 |
| 372px | 2 / 2 / **3** / 2 / 2 / 2 |

`Plan`/`Auto` 在 353px 就降到 2 行，其余在 367px，而 **Approve 一直到最后（373px）才降**。用户手机上其它模式都是 2 行、只有 Approve 是 3 行 ⇒ 设备落在 366–372px 那一档。

### 与既有测试的冲突（重要）

`permissionModeLabels.i18n.test.ts` 有一条测试断言短标签长度 ≤ 7 字符，注释写着：

> The whole point of the short labels is that the composer footer does not wrap at 375px.

**这条理由在本设计落地后被取代。**「短标签」这个手段只够把 `Bypass Permissions` (18) 收到 `Bypass` (6)；但它按**字符数**做预算，而折行取决于**像素宽度** —— `Approve` 与 `Default` 同为 7 字符，却差 6px。所以它既拦不住本 bug，也不该继续充当「375px 不折行」这个结论的依据。

（该测试本身保留，理由换成「否则手机上的标签会被截断」；见 §2.4。）

## 1. 决策汇总

| 项 | 结论 | 理由 |
|---|---|---|
| 验收口径 | **只消除模式间差异**，且 358px 及以上一律 2 行 | 用户选定「只消除差异」；358px 是实测门槛（§3） |
| 消除手段 | 把模式**标签 span** 的最小宽度钉成 48px（`min-w-12 text-center`） | 六种模式占位**按构造相同**，而不是靠调宽度碰运气。这是本设计的全部机制 |
| 为什么钉标签而不是钉按钮 | 钉标签得到的是**精确整数** 82px；钉按钮会留下亚像素尾巴（实测 `Approve` 按钮 `min-w:80px` 时是 80.094px，其余 80.000px —— 又不等了） | §2.1 详述 |
| 48px 这个值 | 略大于今天最宽标签 `Approve` 的自然宽 46.094px | 钉死它**不截断任何现有标签** |
| 手机端模型名上限 | `max-w-24` → `max-w-20`（96px → 80px） | 把「六种模式一律 2 行」的门槛从 **374px 拉到 358px**（实测，见下）。没有它，360–373px 这批主流机器会从「2 行 / 3 行混杂」变成「统一 3 行」 |
| 桌面端 | 类的作用域限定 `< sm`（640px） | 桌面宽度充裕，模型名与标签都该保持内容自适应（§3 实测 `min-width` 在桌面是空操作） |
| 短标签文案 | 不改 | 长度不是根因（同为 7 字符的 `Default` 没事），改文案治不了 6px 的像素差 |

### 被否决的方案

**给模式按钮加 `min-w-20`（80px）。** 看似等价，实测会留亚像素尾巴：按钮 `min-width` 是**边界框**下限，标签内容需要 46.094px 而边界框只给了 62px 内容宽（80 − 16 padding − 2 border），`Approve` 长出去 0.094px ⇒ 按钮 80.094px，其余 80.000px。六者又不相等，只是差异从 6px 缩到 0.094px、落在更少的宽度档上而已。改用更大的整数（81/82px）能盖住标签且无尾巴，但它比「钉标签最小宽」多绕一层，且 82 这个数没有任何自解释性。

**只钉标签（不收紧模型名）。** 能彻底消除模式间差异，但「六种模式一律 2 行」的门槛停在 **374px**：358–373px 这批机器（含 360/366/372 这些常见宽度）会从「2 行 / 3 行混杂」变成**统一的 3 行**。用户要的是统一到 2 行 —— 光统一行数、方向搞反，等于把 bug 从「Approve 特殊」换成「全员退步」。

**只收紧模型名（不钉标签）。** 改动最小，但 Approve 在部分宽度仍与其它模式不一致 —— 治标不治本。

**在 `<sm` 把模型名缩到只剩 `Cpu` 图标。** 门槛能降得最低，但手机上再也看不到当前模型名 —— 实质的功能削减，用户明确不接受。

**把工具栏改成固定两行分区（第一行附件/模式，第二行模型/effort/token/更多）。** 最不脆弱，但要动 `PromptInputTools` 这个通用布局组件，影响所有使用方，超出本 bug 的范围。

## 2. 改动清单

### 2.1 `web/src/components/chat/view/subcomponents/ChatComposer.tsx`（模式标签）

第 575 行的**短标签 span**：

```
-                <span className="whitespace-nowrap sm:hidden">{t(modeLabelKeys.shortKey)}</span>
+                <span className="min-w-12 whitespace-nowrap text-center sm:hidden">{t(modeLabelKeys.shortKey)}</span>
```

`min-w-12` = `12 × 0.25rem` = 48px。按钮宽度随标签固定为
`圆点 10 + 间隔 6 + 48 + padding 16 + 边框 2 = 82px`，六种模式**一模一样**。

`text-center` 让 `Plan`/`Auto` 这类窄标签在 48px 里居中，圆点因此落在所有模式的同一 x 上，与相邻的模型/effort 按钮观感一致。这个类**不需要** `sm:` 变体 —— 它挂在 `sm:hidden` 的那个 span 上，`sm:` 以上整个 span 不显示。

**为什么不是"钉按钮宽"。** 实测对比（同一会话，注入 CSS 模拟）：

| 做法 | 六种模式的按钮宽 |
|---|---|
| 按钮 `min-width: 80px` | `Approve` **80.094px**，其余 80.000px |
| 标签 `min-width: 48px` | 六者全为 **82.000px** |

按钮 `min-width` 管的是边界框；标签内容比内容框宽出 0.094px 时，元素会按内容长出去。钉标签则把内容框本身钉住，得到精确整数。**这个「0.094px 尾巴」不是理论推演，是实测读数** —— 它再次说明折行边界对亚像素敏感，也说明本设计不该去推导闭式公式，只能实测（§3）。

**不变量的真实前提 —— `min-w` 是下限不是上限。** 按钮宽度 = `max(82, 标签自然宽 + 34)`（34 = 圆点 10 + 间隔 6 + padding 16 + 边框 2）。今天六个标签自然宽都 ≤ 46.094px < 48px，所以六者恒为 82。**将来往 `modesShort` 里加更长的标签（例如中文）就会打破它** —— `text-xs` 下 4 个汉字约 48px 就已经顶到边界，再长就直接超过。所以 §2.3 的守卫断言的是「六种模式按钮宽度互差 0px」而不是「都等于 82px」；加标签时它会红，逼人回来重算。这条必须写进代码注释：`permissionModeLabels.i18n.test.ts` 的字符数预算**拦不住**它（字符数与像素宽不是一回事，正是本 bug 的成因）。

### 2.2 `web/src/components/chat/view/subcomponents/ChatComposer.tsx`（模型名）

第 589 行：

```
-                <span className="max-w-24 truncate sm:max-w-32">{modelLabel}</span>
+                <span className="max-w-20 truncate sm:max-w-32">{modelLabel}</span>
```

只改 `< sm` 那一档（96px → 80px）。模型按钮因此 134px → 118px。

**这一项不是可选的，尽管它看起来只是「顺手优化」。** 实测（同一会话、注入 CSS 模拟）：

| 做法 | 六种模式一律 2 行的门槛 |
|---|---|
| 只钉标签（本节不做） | **374px** |
| 钉标签 + 本节 | **358px** |

只做 §2.1 会得到「六种模式行数一致，但 358–373px 一致在 3 行」——差异确实没了，可 360px 这一档主流安卓宽度反而从 2 行退到 3 行。§2.2 才是把结果拉回 2 行的那一半。

按实测，`max-w-20` 已足够（358px 起六模式全 2 行），**不需要**再往下砍。若实现后发现实测与模拟不符，优先复核探针而不是继续砍模型名 —— 那是拿「模型名可见」这个功能换像素门槛。

### 2.3 新增静态守卫 `ChatComposer.toolbar.test.ts`（本设计**核心**）

`web` 测试环境无 DOM（仓库既有约束），量不了布局。所以守卫分两层：

**(a) 静态层（进 CI）**：新建 `web/src/components/chat/view/subcomponents/ChatComposer.toolbar.test.ts`，读 `ChatComposer.tsx` 源码文本，断言三条不变量：

1. 短标签 span 的 `className` 含 `min-w-12`；
2. 同一 span 的 `className` 含 `text-center`；
3. 模型名 span 的 `className` 正好是 `max-w-20 truncate sm:max-w-32`。

三条一起才等价于「六种模式占位相同 + 模型名有上限」。只断言前两条时，把 `max-w-20` 改回 `max-w-24` 测试仍全绿 —— 而那正是「2 行门槛」那一半。

> **失败模式要想清楚**：它读源码文本，所以只针对**单个 class 标记是否存在**（`min-w-12`、`max-w-20 truncate`），不做结构匹配、不数括号、不匹配整条 className —— 多行书写或格式化都不会误红。仓库对「读源码断言结构」有过一次教训（`MessageComponent.test.tsx` 顶部注释记过：多行书写会误红、路由写反却全绿），这里刻意避开那个坑。

**(b) 标签宽度上界**：在 `permissionModeLabels.i18n.test.ts` 的长度断言旁补一句注释，说明「字符数 ≤ 7」与「自然宽 ≤ 46.094px < 48px」是同一个事实的两种表述，且后者才是布局相关的那个 —— 不要把这个换算写成断言（字号一变就假红）。

> 试过但**放弃**的做法：把折行算术抽成 `composerToolbarBudget.ts` 的纯函数 + 像素预算单测。放弃了，因为折行边界有亚像素敏感性（§2.1 的 0.094px、§3 的 1px 档位），把测不准的东西钉成硬数字，第一次换字号/主题就会假红。真正的折行结论由 §3 的浏览器探针给出。

### 2.4 `permissionModeLabels.i18n.test.ts`（修订既有测试）

- **保留** `MAX_SHORT_LABEL_LENGTH = 7` 与长度断言（`Approve` 正好 7；没有理由改小）。
- 把该测试的**名字与注释里的理由**从「否则 footer 在 375px 会折行」改成「否则手机上的标签会被显示不全」——折行现在由 §2.1 的等宽 + §2.2 的上限保证，长度只管可读性。
- 注释里指回本设计，写清「字符数预算为什么不是折行的正确判据」。

## 3. 验证

**静态（可重复，进仓库）**

1. `cd web && npx tsx --test src/components/chat/view/subcomponents/ChatComposer.toolbar.test.ts src/components/chat/view/subcomponents/permissionModeLabels.i18n.test.ts src/components/chat/view/subcomponents/permissionModeLabels.test.ts`
2. `cd web && npm run typecheck`，与改动前 baseline 逐条比对，**零新增**（仓库 baseline 本就不干净）
3. `cd web && npm run lint`，**所改文件**零新增

**动态（一次性；探针放 `/tmp`，不入库 —— 仓库先例是同类探针都不入库）**

用 puppeteer 探针，深链一个多工具会话（例如 `a8b0f512-9209-4da7-bf7c-bd03daf200ab`），逐个点击模式按钮轮换六个模式：

- 模式按钮的识别：`title` 以 `Click to change permission mode` 开头；
- 每次读取 `[data-slot="prompt-input-tools"]` 下**所有 `button`** 的 `getBoundingClientRect()`，按 `top` 聚类（容差 8px）数视觉行数；
- 每个宽度**多点几次并记录每步的按钮文字**，确认六次真的覆盖到六个不同模式（实测第一次点击后的模式由 localStorage 存的值决定，只按次数遍历会漏）。

判定条件：

| 视口 | 期望 |
|---|---|
| 375 / 390 / 393 / 412 / 414 / 430px | 六种模式的行数集合 == `{2}` |
| 358 / 360px | 六种模式的行数集合 == `{2}`（模拟值；若实测是统一的 3 行，如实记录并回头复核 `max-w-20` 是否该再收一档） |
| 344 / 350 / 356px | 六种模式的行数集合大小为 **1**（统一；是几行不作要求） |
| 任意视口 | 六种模式的**模式按钮宽度互差 0px** |
| 640 / 768 / 1024 / 1440px | 六种模式的按钮宽度**互不相同**（内容自适应仍在生效，钉标签没有污染桌面） |

最后一行是**反向断言**，别漏：只验证「手机上一致」会漏掉「桌面也被钉住」这个回归。

**改动前的实测预期（用注入 CSS 模拟得到，实现后应对得上）**

| 视口 | 六模式行数 | 模式按钮宽 |
|---|---|---|
| 344–357px | 3/3/3/3/3/3 | 82px |
| 358px – 639px | 2/2/2/2/2/2 | 82px |
| 640–1440px | 2/2/2/2/2/2 | 91.734 / 94.625 / 100.656 / 107.969 / 109.766 / 140.625（各不相同） |

**门槛的敏感性 —— 实现后必须自己重测，不要相信上表**

上表来自「注入 CSS 模拟」，与真实改类名可能不同（`min-w-12` 经 Tailwind 编译后的具体规则、类名顺序带来的优先级）。模拟把门槛量到 358px（1px 档位扫描，357px 仍是 3 行），闭式算术会算成 356px —— 差 2px。

这正是本设计不写像素公式单测的原因：**折行边界是实测量，不是可推导量。** 实现后按 §3 的 1px 档位扫描重测，以实测为准；判定条件用「358px 是否已恒 2 行」这种可验证的表述，而不是「门槛恰好等于 356」。

**上面两个 374 / 358 都只是模拟值。** 真正要在计划里落地的是三条可验的**不变量**，它们不依赖任何具体门槛数字：

1. **同宽即同行**：任意视口下，六种模式的按钮宽度互差 0px ⇒ 折行结果必然相同（这是本设计要买的东西）。
2. **375px 是 2 行、且六模式一致**：这是既有测试注释里立的标准，也是用户能直接看到的验收点。
3. **桌面不受影响**：≥ 640px 时六模式按钮宽度互不相同。

**探针的两个坑**

- 必须先中和 `content-visibility: auto`（`.chat-message` 带它，屏幕外的行只报占位高度）。工具栏在视口内不受影响，但探针若顺带量消息行会拿到假值。
- 量「模式按钮宽度」时用 `getBoundingClientRect().width` 即可（实测已含 padding + 边框）。

## 4. 不做什么

- 不改 `PromptInputTools` / `PromptInputFooter` 的通用布局。
- 不改短标签文案。
- 不改对话里工具调用行的任何渲染（与本 bug 无关）。
- 不承诺 344–357px 极窄视口为 2 行 —— 那个门槛要砍按钮或藏模型名才过得去。
- 不做 `sm:` 以上的任何调整。

> 这个探针第一版把行数报成 8（每行 1 个），原因是聚类写错了 —— `last` 存的是数组，`last.top` 是 `undefined`，`Math.abs(x - undefined) <= 8` 恒为 `false`。**拿行数做断言前先确认探针本身没坏**：390px 这种明显只该 2 行的宽度上跑一遍，若报出「每行 1 个」就是聚类坏了，不是布局变了。

**关于 `content-visibility: auto`**：`.chat-message` 带它，屏幕外的消息行只报占位高度。所有量消息行的探针都先注入 `* { content-visibility: visible !important }`。工具栏在视口内，不受影响。
